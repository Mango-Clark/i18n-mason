# i18n 아키텍처 조사

English: [discovery.md](discovery.md)

이 문서는 권고나 변경에 앞서 대상 저장소의 현지화 동작을 파악하는 방법을 설명합니다. 프레임워크나 라이브러리를 고르는 안내서가 아니라 근거를 따라가는 조사 절차입니다. 실행 시 따를 간결한 절차는 [스킬 지침](../skills/i18n-mason/SKILL.md)에 있습니다.

## 요청 범위부터 확인하기

감사, 새 로케일 추가, 라우트 변경, 카탈로그 마이그레이션 등 작업에서 바꿀 대상을 확인합니다. 저장소 지침과 `i18n-mason.toml`을 읽고, 요청이 영향을 주는 앱·서비스·플랫폼·사용자 접점을 찾습니다. 모노레포 전체가 같은 계약을 공유한다는 근거가 없다면 일부 범위의 변경을 모든 패키지로 확대하지 않습니다.

요청 범위가 불명확하면 먼저 관련 시스템을 식별할 만큼 조사한 다음, 답에 따라 구현이 달라지는 지점을 변경하기 전에 구체적으로 질문합니다.

## 메시지의 정본부터 사용자까지 추적하기

파일 이름이나 의존성만으로 판단하지 말고 전체 경로의 근거를 확인합니다.

1. **후보 찾기:** 로케일 설정, 메시지 조회, 카탈로그, 라우트 처리, 빌드 스크립트와 현지화 의존성을 검색합니다.
2. **실제 사용 확인:** import와 호출 지점을 따라 런타임 소비자까지 확인합니다. 프로덕션 코드인지 테스트·레거시·선택 기능인지 구분합니다.
3. **소유권 확인:** 스크립트, 생성 헤더, ignore 규칙, CI와 배포 절차를 보고 사람이 편집하는 파일과 도구가 만드는 파일을 나눕니다.
4. **동작 확인:** 사용자에게 제공되는 코드 경로에서 로케일 선택, 라우팅, fallback, 누락 메시지, 서식과 오류를 추적합니다.
5. **교차 확인:** 테스트, 문서, 런타임 검사와 릴리스 설정으로 코드 근거를 확인하거나 한정합니다.

의존성은 사용할 수 있는 기능을 보여줄 뿐 실제 사용을 증명하지 않습니다. 카탈로그가 있다는 사실만으로 모든 메시지가 도달 가능하거나 번역되었다고 볼 수도 없습니다. 테스트 통과는 그 테스트가 실행한 사례와 동작만 입증합니다.

각 발견 사항에는 파일·심볼, 설정 키, 테스트 또는 명령 출력처럼 구체적인 위치와 그 근거가 의미하는 바를 기록합니다. 서로 모순되는 근거도 남깁니다. 생성 파일은 수정 전에 생성기를 거슬러 올라가 정본 입력을 확인합니다.

## 시스템을 나눈 뒤 공유 여부 판단하기

모노레포의 앱, 패키지, 서비스와 네이티브 클라이언트를 각각 조사합니다. 공유 카탈로그가 메시지 정의만 제공하고 앱마다 라우트·로케일 선택·fallback·릴리스 주기는 따로 소유할 수 있습니다. 근거가 있을 때에만 관계를 공유 정본, 공유 런타임, 생성 복사본 또는 미확인으로 기록합니다.

아래 표는 경계를 드러내기 위한 간단한 목록입니다. 공통 디렉터리 구조를 강제하는 규칙은 아닙니다.

| 범위 | 런타임과 진입점 | 로케일 ID와 선택 방식 | 메시지 정본과 소비자 | 생성·배포 경로 | 미확인 사항 |
| --- | --- | --- | --- | --- | --- |
| 웹 앱 | 관찰한 진입점 | 실제 ID와 선택 우선순위 | 정본 리소스 → 조회 지점 | 관찰한 빌드·배포 | 해결되지 않은 사실 |
| API 서비스 | 관찰한 진입점 | 요청·저장 데이터의 로케일 여부 | 응답 또는 서버 문구 소유자 | 관찰한 빌드·배포 | 호환성 경계 |

작업에 필요한 범위만 행으로 추가합니다. 모든 프로젝트에 이 분류나 하나의 공통 구조를 강제하지 않습니다.

## 로케일 동작을 정확히 확인하기

설정, 라우트, API, 저장 데이터, 카탈로그와 플랫폼 인터페이스에 쓰인 로케일 ID를 그대로 보존합니다. `en`, `en-US`, `en-GB`는 서로 다른 공개 계약일 수 있습니다. 차이가 있으면 기록하고 보기 좋게 맞추려고 정규화하지 않습니다.

로케일을 선택하는 실제 입력과 우선순위를 추적합니다. 사용자 설정, URL, 프로필, 세션·쿠키, 브라우저·OS, 요청 헤더, API 매개변수 등이 후보입니다. 관련 웹 동작에서는 리디렉션, 정규 URL, 딥링크, 언어 전환, 링크 생성도 확인합니다. 우선순위가 코드에 없거나 테스트로 확정되지 않으면 미확인으로 기록합니다.

지원·미지원 로케일의 fallback 경로와 누락 키의 개발·CI/빌드·프로덕션 동작을 각각 확인합니다. fallback은 연속적인 사용 경험을 제공하면서 번역 누락을 숨길 수도 있습니다. 라이브러리 기본값이나 설정의 기본 로케일만으로 정책을 추측하지 말고, 실제 적용 설정과 소비 경로를 확인합니다.

## 소유권과 메시지 계약 확인하기

사람이 편집하는 정본, 추출·변환 과정, 생성 산출물, 패키징과 런타임 조회까지 리소스 경로를 추적합니다. 소스 카탈로그가 기능·플랫폼·팀·테넌트·채널별로 나뉘는지 살펴봅니다. TMS나 CMS는 당연히 도입할 개선안이 아니라 실제 소유·배포 방식인지 확인할 대상입니다.

콘텐츠는 소비되는 방식으로 분류합니다. 사용자가 보는 범위에는 UI, 접근성 레이블, 이메일, 알림, CLI 출력, 리포트와 검증 오류가 포함될 수 있습니다. 안정적인 오류 코드, API 필드, 플래그, 경로, 헤더와 프로토콜 값은 번역 문구 옆에 있더라도 기계용일 수 있습니다. 호출 지점과 소비자를 확인하며 겉모양만 보고 번역하거나 이름을 바꾸지 않습니다.

번역 가능한 메시지는 완결된 문장 단위와 그 계약을 확인합니다.

- **placeholder:** 이름·형식·이스케이프와 필요한 값이 모두 전달되는지 확인합니다.
- **ICU 또는 동등 구문:** 각 로케일에서 유효한지, `other` 같은 필수 분기가 있는지 확인합니다. 복수 범주는 언어별로 다릅니다.
- **리치 텍스트·컴포넌트 토큰:** 번역가가 이동하거나 제어할 수 있는 마크업 범위를 확인합니다.
- **서식:** 날짜·숫자·통화·목록·정렬·단위에 프로젝트 또는 플랫폼의 로케일 서식 기능을 쓰는지 확인합니다.

RTL이나 추가 문자 체계가 범위에 있으면 로케일 메타데이터와 런타임 방향, 논리적 레이아웃, 혼합 방향 콘텐츠, 글꼴, 텍스트 확장, 키보드·포커스 동작과 접근성을 확인합니다. 로케일 항목이나 번역 문자열만으로 RTL 사용성을 입증할 수는 없습니다.

## 사실, 추론과 결정을 구분하기

메모와 결과에서 다음 표기를 일관되게 사용합니다.

- **관찰:** 현재 코드, 설정, 테스트 또는 런타임 출력에서 직접 확인한 내용.
- **추론:** 근거와 이유를 제시한 가능성 높은 설명.
- **미확인:** 근거가 없거나 동작을 확정하지 못한 내용.
- **충돌:** TOML 의도와 활성 라우트 ID처럼 권위 있는 두 근거가 다른 상태.
- **권고:** 현재 동작에 대한 설명이 아니라 제안하는 변경.

원하는 상태(`i18n-mason.toml`)와 관찰한 상태를 분리합니다. 충돌은 마이그레이션, 레거시 ID, 환경별 생성 설정 또는 모노레포의 별도 범위에서 비롯될 수 있습니다. 어느 쪽이 잘못됐다고 가정하기 전에 조사합니다.

## 설계를 바꾸는 결정만 질문하기

먼저 조사하고 관련 질문을 묶습니다. 질문마다 확인한 근거, 해결되지 않은 충돌·미지 사항, 답에 따라 달라지는 구현 선택을 함께 설명합니다. 답이 사용자 동작, 호환성, 소유권 등 중요한 제품 경계를 바꿀 때만 질문합니다.

| 영향 | 기본 대응 |
| --- | --- |
| 낮음: 서식 또는 확립된 저장소 규칙 | 기존 규칙을 따릅니다. |
| 중간: 구성 또는 소유권 경계 | 일관된 선례를 따릅니다. 선례가 없거나 새로운 공개·소비 경계를 만들면 묻습니다. |
| 높음: 로케일 ID·기본값, URL, 선택 우선순위, fallback, 누락 정책, 공개 API, 번역 소유권, 마이그레이션, 현지화 범위 | 저장소 근거나 명시된 요구가 결정하지 못하면 묻습니다. |

답변과 무관한 작업은 계속 진행하되, 답변에 의존하는 변경은 보류합니다. 라이브러리의 흔한 기본값을 조용히 선택해 중요한 제품 결정을 구현 세부사항으로 위장하지 않습니다.

## 변경 계획과 결과 검증

마이그레이션 전에 영향 받는 소비자, 정본, 키·로케일 계약, 생성 산출물, fallback, CI·배포 영향과 되돌릴 수 있는 변경 순서를 파악합니다. 변경이 요청 범위가 아니라면 안정적인 키와 기존 동작을 보존합니다. 사용되지 않는다는 사실을 확인한 뒤에만 리소스를 삭제합니다.

주장에 맞는 검사를 선택합니다. 리소스 구문은 파서·카탈로그 검증, 선택·fallback은 집중 테스트, URL 동작은 라우트 테스트, 생성 산출물은 빌드 검사, 방향·레이아웃은 적절한 시각·접근성 검사를 활용합니다. 각 검사가 입증하는 내용과 입증하지 않는 내용을 보고합니다.

### 감사 결과 권장 형식

작업에 맞게 조정하고, 추측을 채우기보다 불필요한 항목은 생략합니다.

1. **조사 범위** — 앱, 서비스, 플랫폼과 사용자 접점.
2. **관찰한 구조** — 런타임, 정확한 로케일 ID, 선택·라우팅, fallback과 누락 동작.
3. **리소스 소유권** — 정본, 생성기, 산출물과 런타임 소비자.
4. **범위와 계약** — 메시지 완성도, placeholder, 서식, 관련 RTL 근거.
5. **발견 사항** — 근거를 붙인 관찰, 추론, 미확인, 충돌.
6. **필요한 결정** — 미결정 질문과 답에 따라 달라지는 선택.
7. **검증과 한계** — 실행한 검사, 뒷받침하는 주장, 확인되지 않은 동작.

서로 다른 저장소에서 기대되는 판단 예시는 [수동 동작 시나리오](../tests/scenarios.ko.md)를 참고하세요.
